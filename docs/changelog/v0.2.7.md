# v0.2.7 — 2026-07-29

## New — `--datatype vcf` reads VCF genotypes directly into the feature matrix
`train`, `evaluate`, `drphylo`, and `aim` now accept `--datatype vcf`, consuming `.vcf` and gzip/bgzip-compressed `.vcf.gz` files directly. Previously the only route from variant calls into MyESL2 was the lab's `VCF2SparseFasta` script, which converts each genotype to a single FASTA character; because that mapping tests only for `0|0`, every non-reference call — `0|1`, `1|0`, `1|1` — collapses to the same symbol, so heterozygosity, phase, and missingness are destroyed before MyESL2 ever sees the data. A FASTA character cannot express "half of this allele" at all. Reading VCF natively removes the intermediate and lets a heterozygote contribute *fractional* evidence to both of its alleles.

Each file in the list is one group ("gene"), following the existing one-file-one-stem convention; sample IDs are taken from the `#CHROM` header line and matched against the hypothesis file by name. Every (site, allele) pair carried by at least one sample becomes a feature column labelled `{stem}_{chrom}:{pos}_{allele}`. The allele is the literal REF/ALT string, so multiallelic sites, indels (`AT`), and symbolic alleles (`<DEL>`) are all first-class — the `GT` field is located by name within `FORMAT` rather than assumed to be first, and sites whose ALT is `.` are skipped as carrying no possible variation.

Internally VCF reuses the **numeric** (float-matrix) path rather than the FASTA path, which is what makes the feature small and the semantics correct. A PFF cell is exactly one byte — one character per (sequence, position) — with nowhere to store `0.5`, whereas the PNF format is already an `N × F` little-endian `float32` matrix with named `feature_labels`. `evaluate` matters as much as `encode` here: its numeric branch resolves model features **by label name** against the cache header, while its FASTA branch decodes the allele as a single `char` (`label[us2 + 1]`), which would silently corrupt any multi-base allele. A new `src/vcf_parser.cpp` therefore writes a `.vnf` cache in the PNF on-disk layout — the distinct extension exists only to keep VCF-derived caches from colliding with `.pnf` caches built from a tabular file of the same stem — and the existing `read_pnf_metadata` / `read_pnf_data` readers are reused verbatim. The metadata-plus-payload writer has been factored out of `tabular_to_pnf` into a shared `numeric::write_pnf()` that both converters call; `.pnf` files produced for tabular numeric input are byte-identical to prior versions.

## New — `--het-mode` controls how heterozygous genotypes are weighted
Because a genotype can carry two different alleles, a heterozygote needs an explicit rule for how much weight each observed allele receives. `--het-mode` selects between three, for a diploid site with `REF=A`, `ALT=G`:

- **`dosage`** (default) — each allele is weighted by *copies of that allele / called copies*, so `0/1` gives `A=0.5, G=0.5`. Stated as a ratio rather than a special case, this generalizes without branching to haploid calls (`0` → `A=1.0`), to polyploid calls, and to multiallelic heterozygotes (`1/2` → `G=0.5, T=0.5`).
- **`presence`** — full weight to every allele present in the genotype, so `0/1` gives `A=1.0, G=1.0`. Presence/absence semantics with no dosage information.
- **`alt-dominant`** — a heterozygote is treated as homozygous-alternate: the reference allele gets `0.0` and each observed alternate `1.0`, so `0/1` gives `A=0.0, G=1.0`. The dominant genetic model, and the closest analogue of what the FASTA route produced.

Homozygous calls encode identically under all three modes (`0/0` → `A=1.0`; `1/1` → `G=1.0`), so the flag only ever changes rows that were previously unrepresentable. Phased (`|`) and unphased (`/`) separators are equivalent for weighting purposes and both parsed. Missing calls (`./.`) encode as all-zero across the site, matching the convention already used for a sample absent from a gene. A partially-called genotype (`./1`) counts only its called copies, so it encodes as `G=1.0` rather than `G=0.5`.

The selected mode is persisted in three places, each guarding a different failure: `preprocess_config` (so `encode` agrees with the conversion), the `.vnf` header's `het_mode` key (so a cache built under one mode is re-converted rather than silently reused under another — the reuse predicate now checks `source_path` **and** `het_mode`), and `vcf_encoding.txt` in the output directory. `evaluate` auto-loads that last file from the weights file's sibling-then-parent directory — the same discovery pattern `feature_normalization.txt` already uses, so both flat output dirs and per-lambda `lambda_N/weights.txt` layouts work — and `drphylo` forwards the mode into its per-clade `evaluate` calls. This matters because a mismatched mode does not fail loudly: the labels still resolve and every score is silently rescaled. `evaluate` also accepts `--het-mode` as an explicit override, and warns when neither a sidecar nor a flag is available before falling back to `dosage`.

## New — VCF filtering, per-site scores, and supporting plumbing
`--min-minor` and `--drop-major-allele` apply to VCF input with the same semantics they have for FASTA, deliberately evaluated at encode time rather than during conversion: carrier counts must be taken over the samples the hypothesis file actually selects (mirroring how the FASTA encoder filters after sample mapping), and `--auto-bit-ct` rewrites `min_minor` from class sizes that `preprocess` never sees. Filtering therefore runs on the assembled float columns, mirroring the FASTA filter order — monomorphic sites are dropped, a site whose non-major carrier total falls below `min_minor` is dropped, and individual allele columns below `min_minor` are dropped — with a carrier defined as a sample holding a non-zero dosage and ties for the major allele resolved to the lexicographically smaller allele label (generalizing the FASTA encoder's lowest-ASCII tie-break). Keeping filtering out of the converter also means the cache can be reused across different `--min-minor` settings without re-parsing the VCF.

Unlike the numeric path, VCF emits per-site significance scores (`pss.txt` / `pss_median.txt`) alongside the per-gene `gss.txt`, since variant positions carry real genomic meaning; the numeric path suppresses PSS only because tabular features have no positional interpretation. Relatedly, `group_var_site_counts` is populated from the true count of retained variant sites per group rather than the feature-count proxy the numeric path substitutes, so `--group-penalty-type` receives a meaningful site count for VCF input.

Supporting changes: `--feature-normalize` is now accepted for `--datatype vcf` as well as `numeric` (it still resolves to `none` by default for VCF, since dosages already share a common 0–1 scale); `taskfile` accepts a `het-mode` key for the `train`, `evaluate`, `drphylo`, and `aim` task types; single-file auto-detection recognizes a bare VCF (a first line of `##fileformat=VCF`, or a `.vcf.gz` extension) so passing one VCF where a list file is expected warns and continues rather than failing obscurely; and a new `pipeline_utils::input_stem()` strips a trailing `.gz` before taking the stem, so `sample.vcf.gz` and `sample.vcf` both yield the gene name `sample` — without it, compressed input would carry `.vcf` through every gene name and a model trained on one form could not be evaluated against the other. `input_stem` is a no-op for `.fasta` / `.txt` / `.vcf` inputs, so existing runs are unaffected.

`--minor-column` and `--tiered-minor-col` are FASTA-encoder features with no float-matrix implementation and are now **rejected with an explicit error** under `--datatype vcf` rather than silently ignored. Multiallelic sites split across several records (one row per ALT, as produced by `bcftools norm -m-`) are also rejected, because the per-record genotypes cannot be recombined unambiguously; the error names `bcftools norm -m+any` as the fix. INFO/QUAL/FILTER-based site filtering is not performed — pre-filter with `bcftools view` if needed — and because the feature matrix is dense, whole-genome VCFs should be split by region and listed as separate files.

zlib is a **required** dependency on Linux and macOS and an optional one on Windows, which has no system zlib: without it, plain `.vcf` still works and a `.vcf.gz` input raises an explicit "rebuild with zlib" error instead of failing the build. Dropping a `zlib.lib` / `zlib1.dll` into `deps/windows-x64/` enables compressed input there with no code change. bgzip output is a multi-member gzip stream, which zlib's `gzgets` reads correctly, so bgzipped VCFs work without BGZF-specific code.

## New — `train` scores its fitted models automatically (`--no-evaluate` to skip)
`train` previously ran `preprocess` → `encode` → `train` and stopped, so a run produced `weights.txt`, `gss.txt`, and the median score files but no per-species predictions at all. The SPS/SPP/SCP scores live in `eval_SPS_SPP.txt`, which only `evaluate` writes, so obtaining them meant a second invocation with the weights path, list file, datatype, and cache directory all restated by hand — and getting any of those wrong (particularly `--datatype`, or `--het-mode` for VCF) produces wrong scores rather than an error. This was not specific to any datatype: FASTA, numeric, and VCF training runs alike produced no prediction files.

`train` now scores every fitted model against the training data as a **Phase 4: Evaluation** step, writing `eval.txt`, `eval_SPS_SPP.txt` (per-species `SPS`, `SPP`, `SCP`), and `eval_gene_predictions.txt` into each `lambda_<N>/` directory. The implementation reuses the per-lambda evaluate loop `drphylo` already ran, so the outputs are identical to what a matching standalone `evaluate` produces. The training hypothesis file is passed through, so classification metrics (accuracy, TPR/TNR, AUC) are printed and logged per model. Settings are read back from the resolved `preprocess_config` rather than from the pre-resolution CLI options, so `cache_dir`, `num_threads`, `datatype`, and `het_mode` all match what the encode phase actually used — the last of these matters because an incorrect genotype encoding silently rescales every VCF dosage instead of failing.

Pass **`--no-evaluate`** to skip the step and restore the previous output set. It is also skipped implicitly under `--method none`, where regression produced no model to score. Visualization remains off in this phase: one SVG heatmap per grid point is rarely useful, and a 9×9 lambda sweep would emit 81 of them. Generate one on demand from any lambda's `eval_gene_predictions.txt` with the standalone `visualize` command. Note that evaluation runs once per grid point, so a large sweep re-reads the feature cache once per model; `--no-evaluate` is the escape hatch when that cost is unwelcome. Model fitting is unaffected — `weights.txt` is byte-identical with and without the new phase. The flag is also accepted by `taskfile` as `no-evaluate: true` under `task_type: train`.

## Behavior change — `train --method` now defaults to `sg_lasso_logisticr`
`train` previously left `--method` empty by default, and an empty method means "skip regression": the run completed preprocessing and encoding, wrote a `lambda_list.txt` containing only the hardcoded default `0.1 0.1` pair, and produced no `lambda_<N>/` directories, no `weights.txt`, and no `train` section in `process_log.txt`. Because nothing errored, a user who supplied a full `--lambda-grid` and omitted `--method` got a silently truncated run whose most visible symptom was a lambda grid that had been replaced by a single unrelated pair. `train` now defaults to `sg_lasso_logisticr`, matching `drphylo`, `aim`, and adaptive sparsification, which already defaulted to it.

The skip-regression path is preserved and is now explicit: pass **`--method none`** to run preprocessing and encoding only. The existing deprecated-alias resolution and the `--nfolds requires --method` guard both key off the same empty-method state, so they compose with the new sentinel unchanged.

## Behavior change — `drphylo` and `aim` validate `--datatype`
`drphylo` and `aim` accepted any string for `--datatype` without validation, so a typo fell through to the FASTA branch and surfaced much later as a confusing `data_defs.ini` lookup failure or `No chars defined for '<typo>'`. All four commands that accept the flag — `train`, `evaluate`, `drphylo`, `aim` — now share a single validator that rejects unknown values up front with the full accepted set in the message (`universal`, `protein`, `nucleotide`, `numeric`, `vcf`). Valid invocations are unaffected.

## Correction to the v0.2.5 release notes — `train` does not auto-generate SVGs
The v0.2.5 changelog entry "Behavior change — default `--gene-limit` and `--species-limit` lowered from 100 to 20" listed `train` among the commands with auto-generated SVG heatmaps. That was inaccurate when published: `train` has never produced an SVG, and it accepts neither `--gene-limit` nor `--species-limit`. `run_train` invokes `preprocess` → `encode` → `train` and nothing else, and no tagged release (v0.2.4 through v0.2.6) contains a visualizer call on that path. The 20 × 20 default described in that entry is real, but applies only to `evaluate`, `drphylo`'s aggregated `eval.svg`, and the standalone `visualize` command. The v0.2.5 entry is left as published; this note is the correction.
